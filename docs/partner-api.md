# Resourceful Partner API

Resourceful's Partner API creates white-label property-analysis cases through the same jurisdiction, service-eligibility, accounting, and durable pipeline controls used by first-party production traffic.

## Authentication

Send the partner key as a Bearer token:

```http
Authorization: Bearer rfl_...
```

Keys are shown once when created. Resourceful stores only the SHA-256 hash.

## Create a report

`POST /api/v1/reports`

Every create request **must** include a stable idempotency key generated by the partner for that logical report request:

```http
Content-Type: application/json
Authorization: Bearer rfl_...
Idempotency-Key: 8f12c4d3-3c71-43dd-b2cc-0bd42077f942
```

Example body:

```json
{
  "property_address": "123 Main St",
  "city": "Naperville",
  "state": "IL",
  "county": "DuPage",
  "property_type": "residential",
  "service_type": "tax_appeal",
  "client_email": "owner@example.com",
  "client_name": "Property Owner",
  "review_tier": "auto"
}
```

Supported `property_type` values are `residential`, `commercial`, `industrial`, and `land`. Supported `service_type` values are `tax_appeal`, `pre_purchase`, and `pre_listing`. Service/review-tier combinations remain subject to Resourceful's server-side eligibility rules.

## Idempotency contract

The `Idempotency-Key` is scoped to the authenticated partner and is stored only in a service-role-only request ledger.

- Repeating the same key with the same validated request body resolves the original report and does not create duplicate usage charges or duplicate pipeline ownership.
- Reusing a key with a different validated request body returns `409 IDEMPOTENCY_KEY_CONFLICT`.
- If the same request is still being created concurrently, Resourceful can return `409 REQUEST_IN_PROGRESS` with `Retry-After: 5`; retry the same key and body.
- Do not generate a new idempotency key merely because a network request timed out. Reuse the original key until the logical create operation is resolved.

## Monthly quotas and accounting

Partner usage is recorded exactly once per report in an immutable usage ledger. Monthly limits are enforced transactionally from ledger entries in the current UTC calendar month; the legacy mutable monthly counter is not the quota authority.

A newly created partner report remains non-runnable until usage accounting succeeds. This prevents over-quota or unaccounted reports from being picked up by pipeline recovery workers.

If the configured monthly limit has been reached, Resourceful returns:

```json
{
  "error": "Monthly report limit exceeded",
  "code": "MONTHLY_REPORT_LIMIT_EXCEEDED",
  "retryable": true
}
```

with HTTP `429`. The same idempotency key can be retried when quota is available again.

## Successful response

A newly created report returns HTTP `201`; an idempotent replay returns HTTP `200`.

```json
{
  "reportId": "uuid",
  "status": "paid",
  "queueStatus": "queued",
  "jurisdiction": {},
  "idempotentReplay": false,
  "message": "Report created and durably queued."
}
```

`queueStatus` reflects durable pipeline ownership, not synchronous report completion. Report generation runs asynchronously through the recoverable worker control plane.

## Other expected errors

- `400 IDEMPOTENCY_KEY_REQUIRED` — missing or invalid idempotency key.
- `400` — request validation failure.
- `401` — missing bearer token.
- `403` — invalid/inactive API key or partner billing is not configured.
- `409` — unsupported service scope, idempotency conflict, or an identical request is still being created.
- `429` — API rate limit or monthly partner report quota reached.
- `503` — address/county verification dependency could not establish a safe jurisdiction decision.

Jurisdiction and service failures are intentionally fail-closed: a partner relationship never bypasses filing-scope, regulated-service, or jurisdiction release gates.
